## 1. Условие задачи (вариант 34)

Посылки поступают в сортировочный центр из нескольких входных пунктов. Каждая посылка имеет уникальный номер, направление доставки и состояние маркировки. Она последовательно проходит входной накопитель, сканирование, сортировку, транспортировку по конвейеру и выходной накопитель своего направления.

Сканеры, сортировщики и конвейеры имеют ограниченную пропускную способность, а накопители — ограниченную вместимость. Если следующий этап заполнен, предыдущий временно приостанавливается. При ошибке чтения маркировки посылка направляется на повторное сканирование либо в накопитель ручной обработки. Число повторных попыток ограничено.

Требуется разработать консольное приложение, моделирующее конвейерную обработку посылок.

### Основные сущности и параметры

- Количество посылок и целевых направлений доставки;
- число входных линий, сканеров и сортировщиков;
- длина и скорость конвейеров;
- вместимость входных, промежуточных и выходных накопителей, очереди повторов и ручной зоны;
- интервалы поступления посылок;
- длительность сканирования и сортировки;
- вероятность ошибки чтения маркировки и лимит повторных попыток.

### Инварианты модели

1. Посылка одновременно находится только на одном этапе технологического процесса.
2. Каждый сканер и сортировщик обрабатывает не более одной посылки одновременно; в одной ячейке конвейера находится не более одной посылки.
3. Вместимость буферов и накопителей не превышается.
4. Посылка направляется к выходу только после распознавания направления.
5. Уникальный идентификатор посылки сохраняется при переходах между стадиями.

Программа завершается после обработки всех сформированных посылок: доставки в выходные накопители или передачи в ручную зону после исчерпания повторов. В неограниченном режиме работа продолжается до прерывания пользователем.

## 2. Архитектура программного решения

Проект реализован на языке C (стандарт C11, POSIX). Моделирование последовательное: в цикле увеличивается номер такта и обновляются состояния устройств.

- `src/parcel.h`, `src/parcel.c` — структура посылки `parcel_t`: идентификатор, линия поступления, направление, статус маркировки (`LABEL_OK`, `LABEL_UNREADABLE`, `LABEL_DAMAGED`), текущая стадия, число повторов, время поступления и завершения.
- `src/center.h`, `src/center.c` — оборудование центра: ограниченные кольцевые очереди `fifo_queue_t`, сканеры `scanner_unit_t`, сортировщики `sorter_unit_t` и конвейеры `conveyor_line_t`. Здесь же находятся выделение и освобождение памяти и функция `center_verify_invariants()`.
- `src/event_sim.h`, `src/event_sim.c` — тактовый цикл и фазы поступления, обработки и перемещения посылок, обслуживание накопителей и итоговая статистика.
- `src/io_logger.h`, `src/io_logger.c` — вывод событий в терминал и журнал через файловые дескрипторы.
- `src/config.h`, `src/config.c` — параметры по умолчанию, разбор CLI через `getopt_long` и чтение конфигурационных файлов `.conf`.
- `src/main.c` — точка входа, настройка обработчиков сигналов через `sigaction`, запуск моделирования и вывод итогового отчёта.

Источники представлены входными линиями с расписанием поступления, устройства — структурами с состоянием занятости и таймером. Каждая посылка хранит своё состояние в отдельной структуре. Потоков в ИЗ-1 нет.

## 3. Особенности реализации

### 3.1. Ввод-вывод через дескрипторы файлов

События и итоговая статистика выводятся через функцию libc `dprintf()` в стандартный вывод (`STDOUT_FILENO`) и дескриптор журнала (`log_fd`). Журнал открывается системным вызовом `open()`. Конфигурационные файлы читаются средствами libc.

### 3.2. Обработка сигналов SIGINT / SIGTERM

При нажатии Ctrl+C или получении SIGTERM обработчик только устанавливает флаг `volatile sig_atomic_t g_sigint_received`. Основной цикл проверяет этот флаг, завершает моделирование, записывает событие остановки и итоговую статистику, затем освобождает ресурсы.

Задержка между тактами выполняется короткими частями с проверкой флага, поэтому для остановки не нужно ждать окончания большой паузы. При прерывании в итогах отдельно указано количество незавершённых посылок.

### 3.3. Моделирование заторов

Если промежуточный накопитель заполнен, сканер удерживает посылку и ожидает (`SCAN_BUFFER_STALL`). Если занят вход конвейера, посылку удерживает сортировщик (`CONVEYOR_STALL`). Аналогично обрабатывается заполнение ручной зоны и очереди повторного сканирования: устройство освобождается только после успешной передачи.

Результат законченного чтения сохраняется в состоянии сканера (`result_ready`). Ожидание свободного места не вызывает нового чтения и не меняет уже определённый результат.

### 3.4. Обратный порядок обновления фаз в такте

Фазы выполняются от выхода ко входу:

1. `sim_phase_service()` — освобождение конечных накопителей, если наступил срок обслуживания;
2. `sim_phase_conveyors()` — продвижение посылок по лентам;
3. `sim_phase_sorters()` — обработка и выдача посылок на конвейеры;
4. `sim_phase_scanners()` — сканирование и передача в следующие накопители;
5. `sim_phase_arrivals()` — приём новых посылок во входные очереди.

Такой порядок не позволяет новой посылке пройти сразу несколько технологических этапов за один такт. Сканер и сортировщик могут после выдачи одной посылки принять следующую; её обработка займёт заданное число последующих тактов.

### 3.5. Повторное сканирование и скорость конвейера

`max_rescan_attempts` задаёт количество повторов **после первого чтения**. Например, значение 2 разрешает не более трёх чтений всего. Приоритет отдаётся очереди `rescan_buffer`. При выборе новой посылки входные линии опрашиваются циклически: после успешного выбора указатель `next_input_line` сдвигается к следующей линии.

Скорость `conveyor_speed` измеряется в ячейках за такт и задаётся отдельно от длины ленты. Каждый микрошаг перемещает посылку на одну ячейку с обратным обходом массива. Без заторов движение по ленте занимает `ceil(conveyor_length / conveyor_speed)` тактов после передачи на неё.

### 3.6. Освобождение конечных накопителей

Порядок вывоза из конечных накопителей в условии не задан. В модели принято простое правило: выходные накопители разгружаются каждые `output_dispatch_interval` тактов, ручная зона — каждые `manual_service_interval` тактов. По умолчанию оба интервала равны 10. Отгрузка и передача оператору отражаются событиями `OUTPUT_SHIPPED` и `MANUAL_SERVICED`.

Это позволяет продолжать обработку при ограниченной вместимости. Доставка в выходной накопитель уже считается завершением обработки; последующая отгрузка повторно не увеличивает число доставленных. Поэтому при завершении последняя партия может оставаться в накопителях.

### 3.7. Проверки модели

На каждом такте проверяются вместимости очередей, соответствие стадий местам хранения, распознанное направление и общий баланс посылок. Все поступившие посылки должны находиться в очередях или устройствах либо уже быть выведены из центра.

При переходе данные посылки копируются с сохранением ID, а предыдущее место освобождается только после успешной передачи. Проверка баланса позволяет заметить изменение общего количества посылок; отдельного поиска одинаковых ID или архива исходных данных в текущей версии нет.

Некорректные параметры и ошибки выделения памяти обрабатываются с диагностикой. Код возврата 1 означает ошибку; 0 — штатное завершение или обработанное прерывание.

### 4.2. Правки, описанные в первоначальном отчёте

В первоначальном отчёте были отмечены следующие проблемы и изменения:

1. **Порядок движения по конвейеру.** Прямой обход массива мог переместить одну посылку сразу через всю ленту. Был введён обратный обход ячеек и порядок фаз от выхода ко входу. Этот принцип сохранён; теперь за такт может выполняться несколько микрошагов согласно заданной скорости.
2. **Ввод-вывод в обработчике сигнала.** Вывод сообщений и статистики был вынесен из обработчика в обычный код программы. При последующей проверке обработчик дополнительно уточнён, как описано ниже.
3. **Подключение заголовков.** Для использования `size_t` был добавлен `<stddef.h>`; в модулях, использующих POSIX-функции, заданы необходимые макросы доступности объявлений.
4. **Приоритет входных линий.** Был добавлен начальный сдвиг опроса `(sc + l) % num_input_lines`. При последующей проверке выяснилось, что он фиксирован для каждого сканера; окончательная версия использует меняющийся указатель выбора линии.
5. **Приоритет повторного сканирования.** Сканер сначала проверяет очередь повторов и только затем берёт новую посылку со входа. Это правило сохранено.

### 4.3. Дополнительная проверка и новые исправления

При последующей проверке с помощью ИИ были найдены ошибки, которые не проявлялись во всех первоначальных примерах. После исправлений примеры были запущены заново, а результаты сверены с журналами.

1. **Потеря посылки при заполнении ручной зоны.** Результат `fifo_push()` не проверялся, но счётчик обработанных посылок увеличивался. Теперь сканер удерживает посылку до успешной передачи; аналогично проверяется передача в очередь повторов.
2. **Изменение результата чтения во время затора.** Пока сканер ожидал свободного места, ошибка чтения разыгрывалась заново. Добавлен флаг `result_ready`, отделяющий завершённое чтение от ожидания передачи.
3. **Неверный счётчик повторов.** Раньше учитывались ошибки чтения, включая последнюю ошибку перед браком. Теперь счётчик увеличивается при фактическом начале повторного сканирования, а лимит означает число повторов после первого чтения.
4. **Заполнение конечных накопителей.** Добавлены периодические отгрузка выходов и освобождение ручной зоны. Ограничения вместимости и ожидание при заполнении сохранены.
5. **Настройка скорости конвейера.** Вместо неиспользуемого параметра времени транспортировки введён действующий `conveyor_speed`.
6. **Опрос входных линий.** Указатель `next_input_line` теперь сдвигается после выбора очереди. При заполнении входа поступление повторяется на следующем такте, а новый случайный интервал назначается только после фактического приёма.
7. **Обработчик сигнала и входные данные.** Из обработчика удалён вызов, изменявший обычный `bool`; оставлена только запись атомарного флага. Вместо `atoi()` используется разбор с проверкой числа и диапазона. Добавлены проверки выделения памяти.
8. **Проверка результатов.** Добавлен простой контроль баланса посылок, а bash-скрипт дополнен примерами с накопителями вместимостью 1. Скрипт проверяет успешное завершение и количество посылок. В Makefile добавлена зависимость от заголовков.

В итоговой версии сохранена обычная последовательная реализация на C и небольшой bash-скрипт. Для сборки и запуска примеров дополнительные языки и тестовые библиотеки не требуются.

## 5. Результаты тестирования

Тестирование проводилось в Linux / WSL. Ниже указаны результаты текущей версии после исправлений.

1. **Базовый тест (`data/normal.conf`).** 25 посылок, 2 сканера, 1 сортировщик, вероятность ошибки 15%. Доставлено 24 посылки (96%), одна направлена в ручную зону. Выполнено 4 повторных чтения, ожиданий нет. Среднее время доставки — 13.29 такта, длительность моделирования — 39 тактов.
2. **Заторы (`data/bottleneck.conf`).** 30 посылок, промежуточный буфер вместимостью 2, сортировка занимает 3 такта. Все 30 посылок доставлены. Выполнено 2 повторных чтения, зафиксировано 325 событий ожидания. Среднее время доставки — 37.97 такта, длительность — 98 тактов.
3. **Высокая вероятность ошибки (`data/high_error.conf`).** 35 посылок, вероятность ошибки 60%, не более двух повторных чтений. Доставлено 28 посылок, 7 (20%) направлены в ручную зону. Выполнено 34 повторных чтения. Длительность — 44 такта.
4. **Параметры CLI.** Запуск `./sort_center -n 15 -d 4 -e 25 -D 0` обработал все 15 посылок: они доставлены по четырём направлениям за 35 тактов.
5. **Малый выход (`data/small_buffers.conf`, `-e 0`).** При вместимости выходного накопителя 1 все 12 посылок доставлены за 220 тактов. Из них 11 отгружены, одна осталась в накопителе.
6. **Малая ручная зона (`data/small_buffers.conf`, `-e 100 -r 0`).** При вместимости ручной зоны 1 все 12 посылок переданы в неё за 220 тактов. Из них 11 переданы оператору, одна осталась в накопителе. Повторных чтений нет.

Во всех шести примерах незавершённых посылок нет. Дополнительно проверены пустой запуск, неверные параметры и остановка по SIGINT/SIGTERM.

В первоначальном отчёте были указаны 13.38 такта среднего времени для базового примера, 244 ожидания и 32.54 такта для заторов, а также 41 «повторное сканирование» для высокого процента ошибок. После исправления поведения сканера, порядка обслуживания входов и счётчика повторов эти результаты изменились. В частности, прежнее значение 41 считало ошибки чтения, а текущее 34 — фактические повторные чтения.

Счётчик ожиданий складывает ожидания отдельных устройств и источников. За один такт могут ждать несколько участников, поэтому это число может превышать длительность моделирования.

Журналы основных примеров: `normal_test.log`, `bottleneck_test.log`, `high_error_test.log`, `cli_test.log`. `sort_center.log` содержит пример запуска с параметрами по умолчанию.

## 6. Инструкция по сборке и запуску

Для сборки нужны компилятор C и Make; для скрипта примеров — bash и стандартные утилиты Linux.

```bash
cd idz1_sort_center

# Сборка проекта
make

# Запуск со стандартными параметрами
./sort_center

# Шесть проверочных примеров из bash-скрипта
make test

# Запуск с конфигурационным файлом
./sort_center -c data/bottleneck.conf

# Настройка длины и скорости конвейера
./sort_center --conveyor-length 7 --conveyor-speed 3 -D 0

# Ручная зона вместимостью 1, без повторных чтений
./sort_center -c data/small_buffers.conf -e 100 -r 0

# Непрерывная работа до Ctrl+C
./sort_center --unlimited --delay 50
```

`make test` вызывает `scripts/run_tests.sh`. Для каждого из шести примеров скрипт проверяет успешное завершение, отсутствие незавершённых посылок и число поступлений и завершений обработки. Ограничение времени одного запуска — 10 секунд.

Параметр `-q` отключает события в терминале, сохраняя параметры и итоговую статистику; журнал продолжает записываться. `-L FILE` задаёт путь журнала, `-S N` — seed, `-D MS` — задержку между тактами. Журнал перезаписывается при каждом запуске. Одинаковые параметры и seed воспроизводят результат при использовании той же реализации `rand()`.

В конфигурациях используется формат `ключ=значение`. Параметры CLI имеют приоритет над файлом. Ноль посылок означает пустой запуск, ноль повторов — только первое чтение. Число устройств, вместимости и длительности должны быть положительными, вероятность ошибки — от 0 до 100%. Список аргументов выводится командой `./sort_center --help`.

Проект также можно открыть в CLion через `CMakeLists.txt` или собрать отдельно:

```bash
cmake -S . -B /tmp/sort-center-build
cmake --build /tmp/sort-center-build
```
