## 1. Условие и этапы проекта

Посылки поступают из нескольких входных линий, проходят сканирование, сортировку, конвейер и выходной накопитель своего направления. Устройства обрабатывают по одной посылке, накопители имеют ограниченную вместимость. При ошибке чтения выполняется заданное количество повторных попыток. Если ни одна не удалась, посылка направляется в ручную зону.

В ИЗ-4 нужно распределить работу между отдельными консольными программами на C. Источники отправляют посылки серверу по TCP. Сервер управляет обработкой и пишет общий журнал. Отдельная программа наблюдения получает этот журнал по TCP. Несколько наблюдателей могут работать одновременно, отключаться и подключаться во время моделирования.

Проект развивается в одной папке `sort_center`. Этапы сохраняются в ветках Git:

- `ind_task1` — последовательная модель с тактовым циклом;
- `ind_task2` — модель с потоками, мьютексами и семафорами;
- `ind_task3` — модель с взаимодействующими процессами;
- `ind_task4` — сервер, источники и наблюдатели с TCP.

[Отчёт ИЗ-1 с первоначальными промптами и историей исправлений](https://github.com/MOVIK36/hse_acos_2026/blob/ind_task1/idz1_sort_center/README.md) остаётся в ветке первой работы.

## 2. Структура программы

| Файлы | Назначение |
|---|---|
| `src/main.c`, `src/config.c` | Разбор адреса, порта и настроек модели |
| `src/tcp.c`, `src/tcp_server.c` | Подключение по TCP, приём команд источников и передача журнала |
| `src/clients/source.c` | Генерация посылок одной входной линии, вывод подтверждений сервера |
| `src/clients/observer.c` | Получение и вывод общего журнала |
| `src/process_sim.c`, `src/center.c` | Процессы устройств и посылок, очереди и семафоры |
| `src/io_logger.c` | Запись событий в журнал и вывод в терминал |
| `scripts/run_tcp_tests.sh` | Проверки сетевого режима |

Один экземпляр `sort_source` соответствует одной входной линии. Сервер `sort_center --server` запускает процессы сканеров, сортировщиков, конвейеров и обслуживания накопителей. Для каждой принятой посылки сервер создаёт отдельный процесс. Внутри сервера используются очереди и семафоры из ИЗ-3. `sort_observer` получает события всех линий и устройств, включая итоги работы.

### 2.1. Как проходит одна посылка

1. Клиент получает настройки своей линии. Случайные интервалы поступления и направления он выбирает сам.
2. Клиент отправляет направление по TCP. Сервер ждёт места во входном накопителе и свободной ячейки для процесса посылки. Затем присваивает ID и отправляет подтверждение.
3. Процесс посылки ставит её во входную FIFO и ждёт результата. Сканер читает маркировку и при необходимости повторяет попытку. Он передаёт посылку в промежуточный буфер или в ручную зону.
4. Сортировщик назначает конвейер. Лента перемещает посылку по ячейкам к выходу. Заполненный накопитель задерживает дальнейшую передачу до отгрузки.
5. При доставке на выход или передаче в ручную зону процесс посылки получает сигнал завершения. Сервер освобождает ячейку после `waitpid()`.

Сервер сохраняет один ID на всех стадиях. Ограничения устройств и накопителей действуют и при одновременной подаче из нескольких линий.

## 3. Обмен и завершение

### 3.1. Команды по TCP

Команды и ответы передаются строками с переводом строки. Номера линий и направлений начинаются с 1.

| Команда клиента | Ответ сервера |
|---|---|
| `SOURCE номер_линии` | `READY направления мин_интервал макс_интервал такт_мс seed` |
| `ADD направление` | `ACCEPT id` после приёма посылки, `DONE` после окончания подачи |
| `WATCH` | Общий журнал от начала запуска, затем новые строки по мере записи |

При неверной команде, номере линии или повторной регистрации той же линии сервер отвечает `ERROR`. Источник ждёт ответа на текущую посылку перед отправкой следующей. Сокеты сервера неблокирующие, поэтому ожидание свободного места на одной линии не останавливает обработку других линий или передачу журнала.

### 3.2. Наблюдение

Сервер пишет события поступления, ожидания места, сканирования, повторов, сортировки, передачи на выход и отгрузки в один файл. Каждый наблюдатель читает его по сети со своей позиции. При новом подключении журнал передаётся с начала, поэтому события до подключения тоже видны. Отключение наблюдателя освобождает его соединение. Медленный наблюдатель получает новые данные по мере готовности сокета.

### 3.3. Завершение

Сервер начинает принимать посылки, когда подключились все входные линии из параметра `-l`. Конечный запуск заканчивается после обработки заданного числа посылок. `-n 0` сразу выводит пустую статистику. В режиме `--unlimited` сервер работает до `Ctrl+C` или `SIGTERM`. Если источник отключился до окончания подачи, сервер завершает моделирование с ошибкой.

При остановке сервер ждёт завершения процессов и записывает итоговую статистику в журнал. Сервер ещё около секунды пытается передать остаток журнала. Наблюдатель читает до закрытия сокета. Если к моменту остановки он сильно отстал, последние строки могут до него не дойти.

## 4. Сборка, запуск и проверки

Нужны Linux, компилятор C и Make. Поддерживается также сборка через CMake. После сборки получаются три программы: `sort_center`, `sort_source` и `sort_observer`.

```bash
cd sort_center
make
```

Пример для одного компьютера. Сначала запустите сервер, затем наблюдателей и источники в отдельных терминалах. Команды выполняются из папки `sort_center`.

```bash
# Сервер, две входные линии
./sort_center --server 127.0.0.1 5000 -c data/normal.conf -D 50 -q -L sort_center.log

# Два наблюдателя, каждый в своём терминале
./sort_observer 127.0.0.1 5000
./sort_observer 127.0.0.1 5000

# По одному источнику для каждой линии
./sort_source 127.0.0.1 5000 1
./sort_source 127.0.0.1 5000 2
```

Наблюдатели необязательны. Если запустить только сервер и источники, каждая линия увидит подтверждения своих посылок. С ключом `-q` сервер выведет в терминал параметры и итоговую статистику.

Чтобы проверить переподключение вручную, запустите сервер с `--unlimited`. Остановите одного наблюдателя через `Ctrl+C` и снова выполните его команду. Остановить весь центр можно через `Ctrl+C` в терминале сервера.

При запуске на нескольких компьютерах укажите IPv4-адрес компьютера с сервером в командах всех клиентов. Сервер можно привязать к этому адресу или к `0.0.0.0`. На всех компьютерах используется один и тот же TCP-порт.

Параметры модели задаются на сервере. Сохранились `-n`, `-d`, `-l`, `-s`, `-o`, `-e`, `-r`, `-S`, `-D`, `-c`, `-L`, `-u`, `-q` и настройки накопителей из `.conf`. CLI имеет приоритет над конфигурацией. `-q` оставляет в терминале сервера параметры и итоги. Журнал по `-L` перезаписывается при запуске, поэтому для одновременных запусков нужны разные файлы. Справка по параметрам — `./sort_center --help`. Команды ИЗ-3 по-прежнему доступны без `--server`.

### Проверочные примеры

```bash
make test
```

Сетевой скрипт проверяет, что источники получили подтверждения с теми же ID, которые сервер записал при поступлении и обработке. Вывод наблюдателей сравнивается с журналом. В проверке переподключения два наблюдателя читают события одновременно, один отключается и запускается снова до окончания работы центра. Оба наблюдателя, которые остались до конца, получают журнал целиком.

Результаты проверок на `127.0.0.1`:

| Пример | Поступило | Доставлено | Ручная зона, всего | Повторных чтений |
|---|---:|---:|---:|---:|
| Малый выход, `-e 0` | 12 | 12 | 0 | 0 |
| Малая ручная зона, `-e 100 -r 0` | 12 | 0 | 12 | 0 |
| Проверка повторов, `-n 6 -e 100 -r 2` | 6 | 0 | 6 | 12 |
| Переподключение наблюдателя, `-n 20 -e 0` | 20 | 20 | 0 | 0 |

В каждом из этих запусков незавершённых посылок нет. Также прошли проверку пустой запуск, обработка 300 посылок с повторным использованием ячеек, остановка по `SIGINT` и `SIGTERM` и отключение источника до окончания подачи. Всего прошли 13 сетевых проверок и 33 проверки локальных режимов ИЗ-3.

## 5. Использование ИИ

В ИЗ-4 я сам решил, где разделить модель по сети. Каждую входную линию я вынес в отдельный клиент, а устройства и очереди оставил на сервере. Так сохранилась обработка посылок из ИЗ-3. Для наблюдателей я выбрал один общий журнал. Сервер запоминает отдельно для каждого клиента, сколько байтов уже отправлено. Это позволяет открыть второй терминал или заново подключить первый во время работы центра.

ИИ я использовал для рутины и небольших вспомогательных фрагментов кода. Ещё я попросил его сверить README с ТЗ и проверить сборку и тесты.

### Проверка результата

В сетевом тесте сравниваются ID из подтверждений источников, журнала поступлений и записей о завершении. Так можно заметить потерю или повтор посылки, даже если общее количество совпало. Для проверки наблюдателя сравнивается весь его вывод с файлом журнала, включая статистику. При проверке отчёта уточнено ограничение этой схемы: при остановке сервера медленный клиент может получить журнал не полностью.
